# 주요 프로시저

[메인 README](../README.md) · [아키텍처 구조도](architecture-overview.md) · [서비스 단계](service-stage.md)

핵심 기능 8개의 처리 순서입니다. 각 단계의 담당 서비스와 실패 시 동작을 함께 적었습니다.
계약(요청·응답)은 `docs/*-contract.md`, 코드 위치는 [호출·데이터 흐름](architecture.md)에 있습니다.

## P1. 공고 동기화 (제공처별 스케줄러)

| 단계 | 담당 | 내용 | 실패 시 |
|---|---|---|---|
| 1 | Core Scheduler | 제공처별 주기(기업마당 정기, 과기정통부·충남 6시간)로 시작 | 다음 주기 재시도 |
| 2 | Client | API 전체 페이지 수집, 전체 건수·필수값 검증, 중복 ID 거부 | 응답 불완전 시 전체 중단, 기존 공개 유지 |
| 3 | Mapper | 정규화(복합 ID·지역·분류·기간), 색인 텍스트 + SHA-256 | — |
| 4 | Core → Elasticsearch | 새 버전 색인 준비 | 실패 시 공개하지 않음 |
| 5 | Core → AI Service → OpenAI → Qdrant | 해시가 바뀐 공고만 임베딩·upsert | 부분 실패 시 공개하지 않음 |
| 6 | Core → MySQL | UPSERT, 사라진 공고 `is_source_present=false`, 세대·지문·건수 갱신 | 트랜잭션 롤백 |

## P2. AI 대화 검색

| 단계 | 담당 | 내용 |
|---|---|---|
| 1 | Web | 검색문 + 확인된 조건(지역·업종·목적) POST |
| 2 | Core → AI | 조건 해석(구조화 출력). 조건 변경 제안이 있으면 사용자 확인 후 재검색 |
| 3 | Core → Elasticsearch | 현재 공개 버전에서 Nori BM25 후보 20 |
| 4 | Core → AI → Qdrant | 질의 임베딩(캐시) → 의미 후보 20 |
| 5 | Core | RRF(k=60) 결합, 접수 상태 필터 |
| 6 | Core → AI → OpenAI | 후보 점수화: 관련도 · 자격 · 지역 충돌 · 인용(후보 본문의 정확한 부분 문자열만) |
| 7 | Core | 인용 재검증, 관련도 총점 내림차순 상위 5건, 관련도와 자격 분리 응답 |
| 실패 | Core | 랭킹 시간 초과는 504, 계약 위반은 503. 화면에서 재시도 |

## P3. 필터 검색 (AI 없음)

1. Web이 키워드·지역·분야·제공처·접수 상태(+K-Startup 전용 조건)를 GET.
2. Core가 공개 스냅샷을 메모리에서 필터·정렬(최신·마감순)·페이지.
3. 자격·추천 필드는 응답에 넣지 않음(태그와 자격을 혼동하지 않도록).

## P4. 원문 근거 질문

1. 사용자가 공고 상세에서 질문을 **명시적으로 제출**해야 시작.
2. Core가 기업마당 공식 상세 HTML 수집 → 제목 일치·식별자 검증 → 본문 추출 → 정규화 텍스트·해시 저장.
3. 해시가 바뀐 경우만 청크(최대 1,500자 × 50) 재색인.
4. AI가 해당 공고 청크 상위 5개를 검색해 답변, 모델은 청크 **번호**만 선택.
5. Core가 번호 → ID 복원, 인용 ⊆ 검색 집합 재검증. 부족하면 `INSUFFICIENT_EVIDENCE` + 인용 없는 안내.

## P5. 신청 문서 준비

| 단계 | 내용 |
|---|---|
| 1 | 관심 공고함 또는 전체 검색에서 공고 선택(기업마당·K-Startup·과기정통부·충남) |
| 2 | 첨부 분석 작업 접수(202) → MySQL 작업 행 → RabbitMQ → Core 소비자가 공식 PDF/HWP/HWPX를 위치 포함 블록으로 파싱 |
| 3 | AI 양식 발견 Agent가 문서·문항 제안. 모든 필드는 허용된 블록의 정확한 원문 인용 필요 |
| 4 | 사용자가 문항별 답변 입력 → AI 입력 해석 Agent가 `PROVIDED`/`UNKNOWN` 제안 → 사용자 확인 후 저장 |
| 5 | 원본 HWP/HWPX/PDF에 답변을 기입해 같은 형식으로 다운로드. 기입 위치 누락은 오류 |
| 경계 | 완성본 자동 생성, 암호화 문서·스캔 PDF·임의 업로드는 미지원 |

## P6. 중복 지원·수혜 검토

1. 공고 2건 이상과 참여 상태(신청·선정·협약·집행·수령) 입력.
2. 실행 접수(202) → 실행 행(Outbox) → RabbitMQ → Core 소비자가 공식 첨부 수집·파싱.
3. AI 단일 Agent가 원문 인용 선택지(800자 이하)에서 번호만 선택, 코드가 근거 ID·인용문 복원.
4. 결과·근거 이력 저장, 화면이 실행 상태를 자동 조회. 기관 확인이 필요한 확정 판단은 기술 오류로 거절.

## P7. 기업 맞춤 일일 리포트

1. 저장된 기업의 지역·업종·지원 목적으로 검색문 구성 → P2와 같은 검색으로 상위 3건.
2. 공고별 원문 근거 답변(P4)으로 서류·자격 요약.
3. 생성 작업과 메일 발송 작업을 별도 큐로 분리, 날짜별 생성 예산으로 중복 방지.
4. 웹 미리보기는 즉시, 정기 메일은 수신 확인·동의 후 SMTP 발송(기본 비활성).

## P8. 비회원 검색 결과 복원

1. 비회원 검색 성공 시 Core가 전체 결과·조건을 Redis에 30분 보관.
2. 로그인 직후 Web이 복원 요청 → 소유 계정 확인 후 결과 반환·삭제.
3. Redis 장애 시 검색은 계속되고 복원만 건너뜀.
