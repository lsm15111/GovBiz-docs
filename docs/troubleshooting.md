## T1. 검색 랭킹 시간 초과로 검색 실패

- **문제**: `서울 AI 창업지원 사업 찾아줘` 검색이 `지원사업을 검색하지 못했습니다`로 끝났다. Core·AI 상태와 색인 준비는
  정상(공개 공고 1,550건)이었고, AI 접근 로그에서 조건 해석·후보 검색은 200이지만 랭킹만 두 차례 503이었다.
  두 번 모두 후보 검색 완료 약 25초 뒤에 실패했다.
- **원인**: 랭킹 모델 25초·Agent 30초 제한 안에 20개 후보 점수화가 끝나지 않았다. 공용 설정 파서가 30초보다 큰 값을
  기본값으로 되돌려 환경변수로 늘려도 반영되지 않았고, 시간 초과와 모델 출력 검증 실패를 모두 503으로 합쳐 화면에서
  구분할 수 없었다. 당시 로그가 예외 종류를 남기지 않아 두 요청의 정확한 예외는 확정하지 않는다.
- **해결**: 랭킹 전용 예산을 분리했다. 모델 45초 · Agent 50초 · Core 랭킹 읽기 55초 · Web 확인 검색 90초.
  `LLM_RANKING_MODEL_TIMEOUT_SECONDS`·`LLM_RANKING_RUN_TIMEOUT_SECONDS`·`AI_RANKING_READ_TIMEOUT`을 추가하고
  잘못된 값은 조용히 대체하지 않고 시작을 거부한다. 시간 초과는 504로 구분하고 화면에서 재시도할 수 있게 했다.
  조건 해석·근거 답변·의미 검색 제한은 그대로 두었다.
- **결과**: 같은 검색이 랭킹 시간 안에 완료된다. 상세 정책·검증은 [검색 랭킹 시간 초과 수정](support-program-ranking-timeout-fix.md).

## T2. 첫 검색 42초

- **문제**: 같은 조건으로 검색을 반복해도 매번 40초 이상 걸렸다.
- **원인**: 단계별 측정 결과 첫 검색 42.467초 중 랭킹 LLM이 37.236초(약 88%), 질의 임베딩 3.645초, 벡터 검색 0.2초였다.
  모든 요청이 임베딩·랭킹을 새로 호출했고 병목은 DB나 벡터 검색이 아니라 모델 호출이었다.
- **해결**: AI Service에 정확 일치 캐시(임베딩 256개·랭킹 128개, 5분)를 두고 동시에 들어온 같은 요청은 한 번만 계산해 재사용한다.
  캐시 키에는 후보 공고 내용·기준일·계약 버전을 모두 넣어 카탈로그가 바뀌면 재사용하지 않는다.
  OpenAI Fast 처리 등급도 같은 조건으로 비교했다.
- **결과**: 같은 검색 두 번째 응답 **42.467초 → 0.484초**, 응답 내용 동일. Fast 처리는 중앙값 41.097초 → 27.165초로
  같은 4개 사례 기준 약 30.4% 단축이지만 토큰 단가가 2배라 랭킹에만 적용했다. 캐시는 프로세스 메모리에만 있어
  재시작·다중 인스턴스에서는 공유되지 않는다. 측정 원표는 [검색 지연 개선](search-latency-20260908.md).

## T3. 서울 기업에 안산 관내 공고 추천

- **문제**: 서울 SW 기업 조건의 실제 검색에서 `안산 관내 기업` 대상 공고 `BIZINFO:PBLN_000000000125900`이 추천됐다.
  지역 조건과 본문은 잘리지 않고 전달됐다.
- **원인**: 모델이 "추가 안산 사업장 여부를 알 수 없다"는 이유로 지역 충돌을 `UNKNOWN`으로 남겼다.
  내부 `regionAssessment` schema 설명에 "하위 지역은 확인된 회사 지역 **안에** 있어야 한다"는 전제가 없었다.
- **해결**: 프롬프트와 schema의 판단 전제를 일치시켰다. 서울 회사 / 서울 서초구 한정 → `UNKNOWN`,
  서울 회사 / 경기 안산시 관내 → `INCOMPATIBLE`, 경기 회사 / 경기 안산시 관내 → `UNKNOWN`.
  후보 수·배점·출력 계약·시간 제한은 바꾸지 않았고 추가 LLM 호출이나 도시별 필터, fallback도 넣지 않았다.
- **결과**: 고정 회귀 검사와 공개 공고 재검사를 통과했다. 상·하위 소재지 구분과 근거 인용 개선은
  [지역 충돌 판정 보완](region-conflict-fast-20260908.md)과 [지역 자격 범위·근거 개선](region-eligibility-scope-fix.md).

## T4. 인용 ID 64자리를 63자리로 복사

- **문제**: 공고 원문 근거 답변(E12 실행)에서 모델이 SHA-256 청크 ID 64자리를 63자리로 복사해 인용 검증에 실패했다.
- **원인**: 긴 해시 문자열을 모델이 그대로 되돌려 주는 출력 계약이었다. 이전 E01 실패는 생성 텍스트가 저장되지 않아
  원인을 확정할 수 없었고, 이번 실패는 저장된 출력으로 확인했다.
- **해결**: 모델은 전달받은 청크의 짧은 배열 번호만 선택하고 Agent가 원래 ID를 복원한다.
  공개 API의 `citationChunkIds` 계약은 유지하고, 범위 밖 번호·중복·근거 부족 인용은 계속 거부한다.
- **결과**: 가상 4건 재확인과 공식 HTML 6건 전체 경로(공식 HTML → Core → MySQL·Qdrant → 임베딩·답변 → 인용)가 성공했다.
  AI Service 전체 테스트 207개 통과. 기록은 [RAG 검수·답변 평가](../evaluation/support-program-evidence/README.md).

## T5. 한국어 복합어 질문의 키워드 후보 누락

- **문제**: 고정 스냅샷 1,422건·질문 300개 평가에서 목표 공고가 20위 밖인 질문이 5개 있었다
  (예: `횡성 소상공인 대출이자`, `화천 관광객 유치 여행사`).
- **원인**: v1 Nori 분석기가 지역명·업종 복합어를 질의와 다른 단위로 분해했고 유사 표현을 처리하지 않았다.
- **해결**: `decompound_mode=discard`, 사용자 사전 규칙, 검색 시점 `synonym_graph`를 적용한 v2 색인 정의를 추가했다.
  v1 정의와 평가 라벨은 바꾸지 않고 새 격리 인덱스에서 v1·v2를 비교했다. `전문가=현장애로`처럼 특정 질문만 맞추는
  부정확한 동의어는 넣지 않았다.
- **결과**: Hit@1 258 → 268, Hit@5 292 → 295, Hit@20 295 → 299, MRR@20 0.9061 → 0.9338 (300개 질문, 모델 API 호출 0회).
  누락 5개 중 4개를 회복했고 순위가 내려간 9개 질문도 보고서에 남겼다. 운영 후보 수는 20개를 유지한다.
  [비교 보고서](../evaluation/support-program-search/runs/lexical-v2-20260913-v1/README.md) · [적용 상세](elasticsearch-lexical-search.md).

## T6. 병합 시 migration 번호 중복

- **문제**: 여러 기능 브랜치가 각자 Flyway migration을 추가한 뒤 main에 병합하면서 같은 `V` 번호가 두 번 나타났다
  (2026-09-14 skn-140 병합 `f9e269ed`에서 확인).
- **원인**: fork → PR → squash merge 흐름에서 각자 브랜치 시작 시점의 마지막 번호를 기준으로 파일을 만들었다.
- **해결**: 병합 직전 main의 마지막 번호를 확인해 새 번호로 다시 배정하고, 이미 적용된 migration은 수정하지 않는다는
  규칙을 유지했다.
- **결과**: 현재 migration 파일 33개가 순서대로 적용된다. Core API의 DB 규칙은 [Core API 개발](../backend/core-api/README.md).

## T7. 프런트엔드 전체 테스트 병렬 실행 시간 초과

- **문제**: 91개 파일 전체를 기본 병렬로 실행하면 기존 화면 테스트 1건이 시간 초과로 실패했다.
- **원인**: 화면 통합 테스트가 많아 기본 worker 수에서 개별 테스트의 대기 시간이 한계를 넘었다.
- **해결**: `pnpm test --maxWorkers=2`로 전체를 재실행한다. 테스트는 `VITE_CORE_API_BASE_URL=http://localhost:8080`을 필요로 한다.
- **결과**: 1,102건 전체 통과, lint·build 통과. 실행 방법은 [Frontend 개발](../frontend/README.md).
